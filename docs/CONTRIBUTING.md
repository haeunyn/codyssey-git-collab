# Contributing Guide

> 이 문서는 **팀원이 분담해서** 작성·보완합니다. 규칙에 이견이 있으면 Issue 로 제안하세요.

## 브랜치 전략 (GitHub Flow)

```
main            항상 "깨지지 않는 상태". 직접 push 금지. PR 로만 병합.
feature/*       작업 단위 브랜치. main 에서 따고, 끝나면 PR 로 되돌아간다.
```

**우리 팀이 GitHub Flow 를 선택한 이유 (3줄)**

1. 브랜치가 `main` 과 `feature/*` 둘뿐이라 **규칙이 단순해 팀원이 헷갈릴 일이 적다.**
2. 모든 변경이 **PR 한 곳**을 지나므로 리뷰와 이력이 자연스럽게 쌓인다.
3. `main` 을 항상 깨지지 않는 상태로 두면 누구든 언제든 거기서 새 작업을 시작할 수 있다.

> Git Flow(develop/release/hotfix)는 배포 주기가 긴 제품에 맞습니다.
> 우리는 배포가 없고 인원이 적어서, 단계가 많으면 오히려 병목이 됩니다.

## 브랜치 네이밍 규칙

```
feature/<이름>-<주제>
```

| 예시 | 설명 |
| --- | --- |
| `feature/haeun-string-utils` | 하은이 문자열 유틸 추가 |
| `feature/haeun-fix-truncate` | 하은이 truncate 버그 수정 |
| `docs/haeun-contributing` | 문서 작업 (feature 대신 docs 접두사 허용) |

- 모두 **소문자**, 단어는 **하이픈(-)** 으로 연결
- 이름을 넣는 이유: 누구 브랜치인지 `git branch -a` 만 봐도 보이게

## 커밋 메시지 컨벤션

```
<type>: <무엇을 어떻게 바꿨는지>
```

| type | 쓰는 때 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경 |
| `refactor` | 동작은 그대로, 구조만 변경 |
| `chore` | 설정·빌드 등 잡일 |

### ✅ 좋은 예

```
feat: add truncate() to string utils
fix: handle empty string in truncate()
docs: add branch naming rules to CONTRIBUTING
```

### ❌ 금지 (과제 명세의 "의미없는 메시지" 판정 기준)

| 금지 | 이유 |
| --- | --- |
| `update`, `fix`, `temp`, `wip`, `final` | 변경 대상을 유추할 수 없음 |
| `bug fix`, `edit file` | 무엇을/왜 바꿨는지 안 드러남 |

> 판단 기준: **커밋 메시지만 보고 `git log` 에서 그 커밋을 찾을 수 있는가?**

## 이슈 규칙

- 모든 작업은 **Issue 를 먼저 만들고** 시작합니다.
- Issue 제목도 커밋과 같은 형식을 권장: `feat: add string utils`
- PR 본문에 **`Closes #이슈번호`** 를 반드시 넣습니다. 병합되면 이슈가 자동으로 닫힙니다.

## PR 작성 규칙

PR 본문에 **최소 아래 4가지**가 들어가야 합니다. ([템플릿](../.github/PULL_REQUEST_TEMPLATE.md)이 자동으로 뜹니다)

| 항목 | 내용 |
| --- | --- |
| 연결 이슈 | `Closes #12` |
| 변경 사항 (What) | 무엇을 바꿨는지 |
| 변경 이유 (Why) | 왜 바꿨는지 |
| 테스트/검증 (How) | 어떻게 확인했는지 |

**병합 조건**
- 리뷰어 **1명 이상 승인(Approve)**
- 리뷰 코멘트가 있다면 **반영 또는 답글** 후 병합

## 코드 리뷰 규칙

### 최소 품질 기준 (과제 필수)

> **"LGTM" / "좋아요" 만 남기는 리뷰는 인정되지 않습니다.**

각 PR 에 **실질 코멘트 1개 이상**이 있어야 합니다. 아래 중 하나면 됩니다.

| 유형 | 예시 |
| --- | --- |
| 질문 | "12번 줄에서 `max_length` 가 0이면 어떻게 되나요?" |
| 대안 제안 | "`if not text:` 대신 `if text is None:` 이 의도에 더 맞지 않을까요?" |
| 리스크 지적 | "이 함수가 None 을 받으면 TypeError 가 날 것 같습니다" |
| 개선 제안 | "docstring 에 사용 예시를 한 줄 넣으면 좋겠습니다" |

- **반드시 특정 라인/파일을 근거로** 답니다 (GitHub 의 라인 코멘트 기능 사용)
- 작성자와 리뷰어 간 **최소 1회 이상 상호작용**(답글 또는 수정 반영)이 기록으로 남아야 합니다

### 리뷰 태도

- 사람이 아니라 **코드**에 대해 말합니다
- 반대할 때는 **이유와 대안**을 함께 적습니다
- 사소한 취향 차이는 `nit:` 접두사를 붙여 "반영 안 해도 됨"을 표시합니다

## 충돌 발생 시 대응 흐름

```
충돌 발견
   ↓
① 팀 채널에 공유       "A 파일에서 B님과 충돌났습니다"
   ↓
② 당사자끼리 상의      어느 쪽을 살릴지 / 둘 다 살릴지 결정
   ↓
③ 해결 후 PR 병합
   ↓
④ docs/conflict-resolution.md 에 기록   ← 빠뜨리지 말 것 (과제 필수)
```

**기록은 해결한 사람이 남깁니다.** 템플릿은 해당 문서에 있습니다.

### ⚠️ 운영 안정성 (과제 제약)

- 공유 브랜치(`main` 포함)에서 **무리한 히스토리 재작성 금지**
- **팀 합의 없이 강제 푸시(`push --force`) / 리베이스 금지**
- 충돌·트러블슈팅은 **재현 가능한 기록**이 남아야 함 (상황·절차·결과·주의점)
