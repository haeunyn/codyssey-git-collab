# Contributing Guide

> 이 문서는 **팀원이 분담해서** 작성·보완합니다. 규칙에 이견이 있으면 Issue 로 제안하세요.

## 개발 환경

| 항목 | 요구사항 |
| --- | --- |
| Python | 3.10 이상 |
| Git | 설치 필수 |
| GitHub | 계정 및 공동 저장소 접근 권한 필요 |
| OS | macOS, Windows, Linux |
| 편집기 | 자유 (VS Code 등) |

### 개발 환경 확인

프로젝트 시작 전 터미널에서 아래 명령어를 실행하여 설치 여부와 버전을 확인합니다.

```bash
git --version
python3 --version
```

Python이 여러 버전 설치되어 있다면 3.10 이상의 버전을 명시하여 실행합니다.

```bash
python3.12 --version
```
위 명령어는 macOS/Linux 환경 기준입니다.

Windows에서는 PowerShell에서 Python Launcher가 설치된 경우 아래 명령어를 사용하여 Python 버전을 확인합니다.

```powershell
py --version
py -3.12 --version
```

Python Launcher가 없는 경우 `python --version`으로 확인할 수 있습니다.

### Git 사용자 정보 설정

커밋 작성자를 식별할 수 있도록 GitHub 계정에 연결된 정보를 설정합니다.

```bash
git config user.name "본인 이름"
git config user.email "GitHub 등록 이메일"
```

공용 PC에서는 인증 토큰이나 비밀번호를 저장하거나 공유하지 않습니다.

이번 프로젝트는 팀 소개 문서를 결과물로 선택했으므로 별도의 Python 라이브러리 설치는 필요하지 않습니다.

## 브랜치 전략 (GitHub Flow)

```
main            항상 "깨지지 않는 상태". 직접 push 금지. PR 로만 병합.
feature/*       작업 단위 브랜치. main 에서 따고, 끝나면 PR 로 되돌아간다.
```

**우리 팀이 GitHub Flow 를 선택한 이유 (3줄)**

1. 브랜치가 `main` 과 `feature/*` 둘뿐이라 **규칙이 단순해 팀원이 헷갈릴 일이 적다.**
2. 모든 변경이 **PR 한 곳**을 지나므로 리뷰와 이력이 자연스럽게 쌓인다.
3. `main` 을 항상 깨지지 않는 상태로 두면 누구든 언제든 거기서 새 작업을 시작할 수 있다.

> Git Flow(develop/release/hotfix)는 배포 주기가 긴 제품에 맞습니다.
> 우리는 배포가 없고 인원이 적어서, 단계가 많으면 오히려 병목이 됩니다.

## 브랜치 네이밍 규칙

```
feature/<이름>-<주제>
```

| 예시 | 설명 |
| --- | --- |
| `feature/haeun-intro` | 팀원 자기소개 추가 |
| `feature/geewon-dev-env` | 개발 환경 문서 작성 |
| `feature/geewon-revert` | revert 트러블슈팅 실습 |

- 모두 소문자로 작성한다.
- 단어는 하이픈(-)으로 연결한다.
- 이름과 작업 주제를 포함하여 담당자와 작업 내용을 쉽게 파악할 수 있도록 한다.
- 문서 작업을 포함한 모든 작업 브랜치는 `feature/` 접두사로 통일한다.
- 작업 시작 전 Issue를 생성하거나 배정받고, 최신 `main`을 기준으로 브랜치를 생성한다.
- 하나의 브랜치에서는 하나의 작업 단위를 진행한다.
- 작업 완료 후 PR을 생성하고, 팀원 리뷰 및 승인을 거쳐 `main`에 병합한다.

### 브랜치 생성 예시

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/geewon-dev-env
```

브랜치 이름을 통일하는 이유는 팀원 간 작업을 쉽게 식별하고, 과제에서 요구하는 GitHub Flow 전략을 일관되게 적용하기 위해서이다.

## 커밋 메시지 컨벤션

### 기본 형식

```
<type>: <무엇을 어떻게 바꿨는지>
```

| type | 사용하는 경우 |
| --- | --- |
| feat | 새로운 기능 추가 |
| fix | 오류 및 문제 수정 |
| docs | 문서 추가 및 수정 |
| refactor | 기능 변경 없이 코드 구조 개선 |
| chore | 프로젝트 설정 및 환경 관리 |
| test | 테스트 추가 및 수정 |

### 작성 규칙

- type은 소문자로 작성한다.
- type 뒤에 콜론(:)과 공백 한 칸을 넣는다.
- 변경 대상과 변경 내용을 구체적으로 작성한다.
- 하나의 커밋에는 하나의 논리적인 변경 단위를 담는다.
- 팀 소개 및 협업 문서 작업에는 docs를 사용한다.
- 리뷰 의견을 반영할 때도 수정 내용을 구체적으로 작성한다.

### ✅ 좋은 예

```
docs: add geewon team introduction
docs: add development environment to CONTRIBUTING
docs: improve branch naming rules
docs: record git stash experiment
docs: add team role based on review feedback
fix: resolve README merge conflict
chore: add pull request template
```

### ❌ 금지되는 커밋 메시지

| 금지 예시 | 이유 |
| --- | --- |
| update | 변경 대상을 알 수 없음 |
| fix | 무엇을 수정했는지 알 수 없음 |
| temp, wip, final | 구체적인 작업 내용이 없음 |
| bug fix | 어떤 오류를 수정했는지 알 수 없음 |
| edit file | 어떤 파일을 왜 수정했는지 알 수 없음 |

커밋 메시지만 확인해도 팀원이 변경 내용을 파악할 수 있도록 작성한다.

의미 있는 커밋 메시지는 변경 이력을 추적하고,
문제 발생 시 원인을 파악하는 데 도움이 된다.

## 이슈 규칙

- 모든 작업은 **Issue 를 먼저 만들고** 시작합니다.
- Issue 제목도 커밋과 같은 형식을 권장: `feat: add string utils`
- PR 본문에 **`Closes #이슈번호`** 를 반드시 넣습니다. 병합되면 이슈가 자동으로 닫힙니다.

## PR 작성 규칙

PR 본문에 **최소 아래 4가지**가 들어가야 합니다. ([템플릿](../.github/PULL_REQUEST_TEMPLATE.md)이 자동으로 뜹니다)

| 항목 | 내용 |
| --- | --- |
| 연결 이슈 | `Closes #12` |
| 변경 사항 (What) | 무엇을 바꿨는지 |
| 변경 이유 (Why) | 왜 바꿨는지 |
| 테스트/검증 (How) | 어떻게 확인했는지 |

**병합 조건**
- 리뷰어 **1명 이상 승인(Approve)**
- 리뷰 코멘트가 있다면 **반영 또는 답글** 후 병합

## 코드 리뷰 규칙

### 최소 품질 기준 (과제 필수)

> **"LGTM" / "좋아요" 만 남기는 리뷰는 인정되지 않습니다.**

각 PR 에 **실질 코멘트 1개 이상**이 있어야 합니다. 아래 중 하나면 됩니다.

| 유형 | 예시 |
| --- | --- |
| 질문 | "154번 줄 `git -c credential.helper= push` 는 개인 환경 우회용인가요? 재현할 때 헷갈릴 것 같습니다" |
| 대안 제안 | "`/team/` 소유자가 한 명뿐이라 본인 PR 엔 리뷰어가 자동 지정되지 않습니다. 한 명 더 추가하면 어떨까요?" |
| 리스크 지적 | "이 줄은 #8 과 같은 hunk 라 나중에 병합되는 쪽에서 충돌이 날 것 같습니다" |
| 개선 제안 | "SUBMISSION 의 PR 칸에 #20 이 빠져 있어 평가자가 PR 을 1개로 셀 것 같습니다" |

- **반드시 특정 라인/파일을 근거로** 답니다 (GitHub 의 라인 코멘트 기능 사용)
  - 바뀐 범위 밖의 줄이라 라인 코멘트가 안 달리면, 파일 헤더의 💬(파일 코멘트)를 사용합니다
- 작성자와 리뷰어 간 **최소 1회 이상 상호작용**(답글 또는 수정 반영)이 기록으로 남아야 합니다

### 리뷰어 지정과 기한

- 리뷰어는 [`CODEOWNERS`](../.github/CODEOWNERS) 가 자동 지정합니다. 비어 있으면 작성자가 **직접 1명 이상** 지정합니다.
- 리뷰 요청을 받으면 **24시간 안에** 리뷰하거나, 늦어질 경우 PR 에 한 줄 남깁니다.

### 리뷰 상태 선택 기준

| 상태 | 언제 |
| --- | --- |
| **Comment** | 질문·제안이 있어 작성자의 답을 먼저 듣고 싶을 때 (기본값) |
| **Approve** | 지금 상태로 병합해도 될 때. 사소한 `nit:` 만 남았다면 Approve 와 함께 달아도 된다 |
| **Request changes** | 병합 전에 **반드시** 고쳐야 할 때 (링크 깨짐, 충돌 마커 잔존, 기록 누락 등) |

> 우리 팀은 **Comment 로 먼저 제출 → 반영·답글 확인 → Approve** 순서를 권장합니다.
> 리뷰어–작성자 상호작용이 기록으로 확실히 남기 때문입니다.

### 코멘트 접두사

| 접두사 | 의미 | 반영 |
| --- | --- | --- |
| `question:` | 의도를 묻는 질문 | 답글 필수 |
| `suggestion:` | 대안 제안 | 반영 또는 미반영 이유 답글 |
| `nit:` | 사소한 취향 차이 | 반영 안 해도 됨 |

- 한두 줄 수정 제안은 코멘트에서 ` ```suggestion ` 블록을 쓰면 작성자가 **Commit suggestion** 버튼으로 바로 반영할 수 있습니다.

### 리뷰 반영 절차

```
① 리뷰 코멘트 확인
   ↓
② 같은 브랜치에 반영 커밋 push      예) docs: fix table spacing in intro (review feedback)
   ↓
③ 해당 스레드에 답글                "abc1234 에서 반영했습니다" (반영하지 않으면 이유를 답글로)
   ↓
④ 리뷰어가 확인 후 Resolve conversation
   ↓
⑤ 작성자가 Re-request review → 리뷰어 Approve → 작성자가 병합
```

- 반영 커밋 메시지에는 **무엇을 고쳤는지**를 쓰고, 본문에 어떤 리뷰를 반영했는지 적습니다.
- **커밋만 하고 답글을 빠뜨리지 않습니다.** 답글이 있어야 평가자가 리뷰 → 반영 흐름을 따라갈 수 있습니다.
- 대화 Resolve 는 **리뷰어**가 합니다. 작성자가 스스로 닫으면 리뷰어가 확인했는지 알 수 없습니다.
- 이미 push 한 커밋은 amend/rebase 로 고치지 않고 **새 커밋을 쌓습니다** (강제 푸시 금지).

### 문서 PR 리뷰 체크리스트

리뷰어는 최소 아래 항목을 확인합니다.

- [ ] PR 본문에 `Closes #이슈번호` 와 What / Why / How 가 있다
- [ ] 커밋 메시지가 컨벤션(`<type>: ...`)을 따른다
- [ ] 문서 안 링크가 실제 파일·섹션으로 연결된다 (Files changed → View file 에서 클릭)
- [ ] 표 · 코드 블록이 깨지지 않고 렌더링된다
- [ ] 충돌 마커(`<<<<<<<`, `=======`, `>>>>>>>`)가 남아 있지 않다
- [ ] 기록 문서라면 참여자 이름 · 실제 명령 · 결과가 들어 있다
- [ ] `SUBMISSION.md` 본인 칸이 필요하면 함께 업데이트됐다

### 리뷰 태도

- 사람이 아니라 **코드(문서)** 에 대해 말합니다
- 반대할 때는 **이유와 대안**을 함께 적습니다
- 반영해 준 리뷰에는 짧게라도 확인 답글을 남깁니다

## 충돌 발생 시 대응 흐름

```
충돌 발견
   ↓
① 팀 채널에 공유       "A 파일에서 B님과 충돌났습니다"
   ↓
② 당사자끼리 상의      어느 쪽을 살릴지 / 둘 다 살릴지 결정
   ↓
③ 해결 후 PR 병합
   ↓
④ docs/conflict-resolution.md 에 기록   ← 빠뜨리지 말 것 (과제 필수)
```

**기록은 해결한 사람이 남깁니다.** 템플릿은 해당 문서에 있습니다.

### ⚠️ 운영 안정성 (과제 제약)

- 공유 브랜치(`main` 포함)에서 **무리한 히스토리 재작성 금지**
- **팀 합의 없이 강제 푸시(`push --force`) / 리베이스 금지**
- 충돌·트러블슈팅은 **재현 가능한 기록**이 남아야 함 (상황·절차·결과·주의점)
